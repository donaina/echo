# The ledger model

The wallet service owns money state. This document is the complete description of how
that state is shaped and why.

Read it before changing anything that writes an entry.

---

## The three tables

```
accounts ──< entries >── transactions
                │
                └─< holds
```

- An **account** holds a balance in one currency, for one owner, in one state.
- A **transaction** is one atomic event: a set of entries that sum to zero.
- An **entry** is one leg of a transaction: a signed change to one account.
- A **hold** reserves part of an account's balance without moving it.

Nothing else in the schema moves money.

## The sign convention

`entries.delta_minor` is signed and means: **the change to this account's ledger
balance.**

- Positive — the balance increases (a credit to the holder).
- Negative — the balance decreases (a debit from the holder).
- Never zero.

The entries of a transaction sum to zero, in each currency. That is the whole of
double-entry as implemented here:

```sql
SELECT COALESCE(SUM(delta_minor), 0)
FROM entries
WHERE transaction_id = $1;
-- must be 0
```

There is no separate debit/credit column and no "which side" field. The sign is the
side. This removes a class of bug where a row's type and its amount disagree.

Mapping to the core's debit and credit legs is explicit and lives in the posting
adapter (S7), because that mapping depends on the core's account-type semantics, not
on ours.

## Balances

Two numbers, both derived, neither stored:

```
ledger_balance    = Σ delta_minor over all entries of the account
available_balance = ledger_balance − Σ amount_minor of open holds
```

- `ledger_balance` is what the account owns.
- `available_balance` is what can be spent now.
- They are equal when there are no open holds.

The API reports both. A movement is permitted only against `available_balance`.

### Derivation at scale

`ledger_balance` is computed as:

```
balance of the latest verified checkpoint  (or 0)
+ Σ delta_minor of entries strictly after the checkpoint's boundary
```

A checkpoint is created only by a job that locks the account and computes the exact
balance from scratch. An integrity job recomputes and compares; a checkpoint that
disagrees is deleted, not repaired.

**There is no stored balance column, ever.** A checkpoint is a different object: it is
a boundary plus an exact total, verified, and disposable. The rule that distinguishes
them is simple — if a value can be wrong and nobody notices, it is a cache and it is
not allowed. A checkpoint that is wrong is detected by the job that exists only to
detect it.

## Transactions

| Field | Meaning |
|---|---|
| `id` | ULID, generated by the wallet at write time |
| `operation_type` | Closed list, below |
| `status` | `posted` or `reversed` |
| `occurred_at` | When the platform learned of it, UTC |
| `value_date` | The business date it belongs to |
| `correlation_id` | The request or event that caused the whole chain |
| `causation_id` | The immediate parent (an event id, usually) |
| `created_by` | User id or service identity |
| `reverses_id` | Set only on a reversal; unique |
| `reference` | Human and downstream reference, unique per purpose |
| `metadata` | JSONB for non-monetary context; never an amount |

### Operation types

The closed list. Adding one is an ADR.

| Type | Meaning | Typical legs |
|---|---|---|
| `fund-wallet` | Money entering a wallet | source −, wallet + |
| `withdraw-wallet` | Money leaving a wallet | wallet −, destination + |
| `internal-transfer` | Between two wallets in the platform | from −, to + |
| `fee` | A charge collected | account −, fee account + |
| `fx-settlement` | One side of a currency conversion | account −, FX account + |
| `reversal` | Undo of a prior transaction | mirror of the original |

### Reversal

A reversal is a new transaction with `reverses_id` set to the original, entries that
mirror the original exactly, and its own audit fields. The original moves to
`status = 'reversed'` in the same database transaction.

- A transaction can be reversed once. The unique index on `reverses_id` enforces it.
- A reversal can itself be reversed (a mistaken reversal), and the chain is visible
  through `reverses_id`.
- Nothing is ever deleted. A reversed transaction with its entries remains readable.

## Holds

```
open ──capture──> captured   (money moved; the hold produced entries)
  │
  ├──release──> released     (money never moved)
  └──expire───> expired      (time passed; released by the sweeper)
```

| Property | Rule |
|---|---|
| Amount | Positive, in the account's currency |
| Effect | Reduces `available_balance`; never changes `ledger_balance` |
| Capture | Requires a transaction; the hold links to it |
| Capture effect | The referenced transaction's entries are the movement |
| Release | Idempotent; a second release is a distinct result, not an error |
| Expiry | A safety net for sagas that died; the primary path is explicit release |
| Review holds | Type `review`, never expire, never auto-capture; released only by command |

Holds do not produce entries. A hold is a claim on future money; an entry is money
that moved.

## Accounts

| Type | Purpose |
|---|---|
| `wallet` | A customer's account. Owner is a user id |
| `fee` | Where fees are collected. One per currency |
| `suspense` | Where an unexplained leg lands. Must be zero daily |
| `settlement` | Position with a counterparty (core, rail). One per counterparty per currency |
| `fx` | The FX counterparty account for conversions. One per currency |

- A `wallet` account is unique per `(owner_ref, currency)`.
- A `frozen` account can receive credits but cannot be debited. A `closed` account can
  do neither; its balance must be zero, or the closure fails.
- An account with a non-zero balance cannot be closed.

## Invariants, restated exactly

These are the statements that must hold at every commit point.

1. For every transaction `t`: `SUM(delta_minor) WHERE transaction_id = t` is `0`.
2. For every currency `c`: the sum of all entries in `c` across all accounts is `0`.
3. For every account `a`: `Σ open holds ≤ ledger_balance(a)`.
4. For every transaction: at least two entries, all in the same currency.
5. For every entry: `delta_minor ≠ 0`.
6. For every reversal: entries mirror the original, and the original is `reversed`.
7. No entry exists whose transaction is not `posted` or `reversed`.
8. No hold is `captured` without a linked transaction.

The integrity job checks 1, 2, 3, 6 and 8 continuously. The database enforces 4 and 5.
The Go layer enforces all of them before writing, so the database catches what the
code misses.

## Worked examples

**Wallet funding of 2,500.00 NGN (250,000 kobo) from the core settlement account.**

```
transaction  op=fund-wallet  ref=ECHO-20261124-0007X3
  entry  account=settlement_NGN   delta_cents=-250000
  entry  account=wallet_alice     delta_cents=+250000
  sum = 0
```

**An internal transfer of 100.00 from Alice to Bob.**

```
transaction  op=internal-transfer
  entry  account=wallet_alice   delta_cents=-10000
  entry  account=wallet_bob     delta_cents=+10000
  sum = 0
```

**An outbound rail transfer of 50.00, with a 1.00 fee.**

Two transactions, because a fee is its own operation and its own line of business:

```
transaction  op=withdraw-wallet
  entry  wallet_alice          -5000
  entry  rail_settlement_NGN   +5000

transaction  op=fee
  entry  wallet_alice          -100
  entry  fee_NGN               +100
```

Doing this as one transaction with three legs would also balance, and it would be
wrong: the fee is not part of the transfer, and merging them makes the fee impossible
to reverse independently.

## What this model deliberately omits

- **No mutable balance.** Explained above.
- **No per-account sequence number on entries.** Ordering comes from `(created_at, id)`;
  a sequence would create a write hotspot per account for a benefit the ledger does not
  need. Where strict ordering matters (the saga), the saga has its own state.
- **No soft-deleted rows.** Reversal is the only correction.
- **No currency table.** ISO 4217 codes are validated by pattern and by an enumerated
  list in code; exchange rates are not the ledger's business.
