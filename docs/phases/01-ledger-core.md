# S1 — Ledger core

**Weeks 3–4 · Gate G2 · Owner: ledger engineer**

## Purpose

Build the part of the system that every later stage trusts: accounts, transactions,
entries, and the rule that a balance is the sum of its entries. No HTTP, no
authentication, no events. A library and a schema that cannot drift.

By the end of this stage there is one correct way to move money in the database, and
it is possible to prove it with tests that do not involve a network at all.

## Depends on

S0. The migration tooling, the test harness with a real Postgres, and the platform
package.

## Exit criterion

A test creates two accounts, posts a transaction between them, and derives both
balances from entries. A second test attempts to post an unbalanced transaction and
the database rejects it. A third test reverses the first transaction and both
balances return to their starting values — with four entries on record, not two.

## Gate

**G2 — integration-ready.** The ledger is correct in isolation and its invariants are
enforced by the schema, not only by the Go code.

## Why this stage exists

Because the ledger is the only component whose bugs cannot be corrected by a deploy.
Wrong code can be fixed; a wrong balance has already been spent. Everything else —
the API, the saga, the rail — is a way of asking the ledger to do something. If the
ledger is right and the perimeter is wrong, money is safe and features are missing.
The reverse has no remedy.

## What you build

### The schema

Three tables in `db/wallet/`. Names are the contract; other services will reference
these concepts, so get them right here.

```sql
CREATE TABLE accounts (
  id            TEXT PRIMARY KEY,              -- ULID, generated by the service
  owner_ref     TEXT NOT NULL,                 -- opaque reference from auth/back office
  account_type  TEXT NOT NULL,                 -- 'wallet', 'fee', 'suspense', 'settlement'
  currency      TEXT NOT NULL,                 -- ISO 4217, uppercase
  status        TEXT NOT NULL DEFAULT 'active',-- 'active', 'frozen', 'closed'
  created_at    TIMESTAMPTZ NOT NULL,
  updated_at    TIMESTAMPTZ NOT NULL,
  version       BIGINT NOT NULL DEFAULT 1,
  CONSTRAINT accounts_status_chk CHECK (status IN ('active','frozen','closed')),
  CONSTRAINT accounts_currency_chk CHECK (currency ~ '^[A-Z]{3}$')
);
CREATE UNIQUE INDEX accounts_owner_currency_uq
  ON accounts (owner_ref, currency) WHERE account_type = 'wallet';

CREATE TABLE transactions (
  id               TEXT PRIMARY KEY,           -- ULID
  operation_type   TEXT NOT NULL,              -- closed list, see below
  status           TEXT NOT NULL,              -- 'posted' | 'reversed'
  occurred_at      TIMESTAMPTZ NOT NULL,
  value_date       DATE NOT NULL,
  correlation_id   TEXT NOT NULL,
  causation_id     TEXT,                       -- the event or request that caused this
  created_by       TEXT NOT NULL,              -- service identity or operator
  reverses_id      TEXT REFERENCES transactions(id),
  metadata         JSONB NOT NULL DEFAULT '{}',
  CONSTRAINT transactions_status_chk CHECK (status IN ('posted','reversed')),
  CONSTRAINT transactions_reversal_chk CHECK (status <> 'reversed' OR reverses_id IS NULL)
);
CREATE UNIQUE INDEX transactions_reverses_uq ON transactions (reverses_id)
  WHERE reverses_id IS NOT NULL;

CREATE TABLE entries (
  id              TEXT PRIMARY KEY,            -- ULID
  transaction_id  TEXT NOT NULL REFERENCES transactions(id),
  account_id      TEXT NOT NULL REFERENCES accounts(id),
  delta_minor     BIGINT NOT NULL,             -- signed change to the account's ledger balance
  currency        TEXT NOT NULL,
  created_at      TIMESTAMPTZ NOT NULL,
  CONSTRAINT entries_nonzero_chk CHECK (delta_minor <> 0)
);
CREATE INDEX entries_account_created_idx ON entries (account_id, created_at, id);
CREATE INDEX entries_transaction_idx     ON entries (transaction_id);
```

**`delta_minor` is signed and means "change to this account's ledger balance".**
Positive increases it (a credit), negative decreases it (a debit). That convention is
deliberate: it makes Article III a literal `SUM() = 0` rather than a sum over a case
expression, and it removes any argument about which side is which. Mapping to the
core's debit/credit legs is the posting adapter's job (S7) and is written down there.

### The domain package

`internal/ledger` — pure Go, no `pgx`, no HTTP. It owns the types and the rules.

- [ ] `Account`, `Transaction`, `Entry` types and their construction functions.
      No exported struct literals; constructors validate.
- [ ] `BuildTransfer(entries ...Leg) (Transaction, error)` — the function that refuses
      an unbalanced set. It is the only constructor for a multi-leg transaction.
- [ ] Currency equality: every leg of a transaction is in the same currency, or the
      transaction is rejected. Multi-currency is two transactions plus an FX
      settlement account, not one mixed transaction.
- [ ] The closed list of operation types, defined once:
      `fund-wallet`, `withdraw-wallet`, `internal-transfer`, `fee`, `fx-settlement`,
      `reversal`. See `reference/ledger-model.md`.
- [ ] `Balance(accountID) (int64, error)` at the domain level, and a store method that
      computes it with a single aggregate query.

### The store

- [ ] `PostTransaction(ctx, tx) error` — writes the transaction and all its entries in
      one database transaction, with the zero-sum check repeated as a constraint or a
      statement-level assertion. If the sum is not zero, nothing is written.
- [ ] `EntryBalance(ctx, accountID) (int64, error)` — `SELECT COALESCE(SUM(delta_minor),0)`
      with the index in place.
- [ ] `Reverse(ctx, transactionID, reason, by) (Transaction, error)` — creates the
      equal-and-opposite transaction, sets the original to `reversed`, in one database
      transaction. Refuses to reverse twice (the unique index does this).
- [ ] An `sqlc` query file per operation. Generated code is committed and checked in CI.

### Suspense and system accounts

- [ ] Seed migrations create the system accounts every deployment needs: one `fee`
      account per currency, one `suspense` account per currency, and one `settlement`
      account per currency per rail (the rail one may wait until S8, but the table
      shape exists now).

A transaction that cannot immediately find its other leg posts to suspense. Suspense
must reach zero daily; a balance in suspense is a break, and `recon` (S7+) will treat
it as one.

### Seeding and fixtures

- [ ] A `testkit` helper that creates an account with an opening balance by posting a
      real funding transaction from the appropriate system account. Tests never insert
      entries directly; if a test needs a balance, it earns it through the ledger.

## Data model changes

The three tables above, plus the system-account seed. No holds yet — that is S3.

## API surface

None over the network. The package API in `internal/ledger`:

| Function | Contract |
|---|---|
| `NewAccount(...)` | Validates currency, type, owner. Returns an `Account`. |
| `BuildTransfer(legs...)` | Rejects unbalanced or mixed-currency sets. |
| `Store.PostTransaction` | Atomic; zero-sum enforced twice (Go and SQL). |
| `Store.Reverse` | Atomic; idempotent by unique index; never deletes. |
| `Store.EntryBalance` | Exact; derived from entries; no stored column. |

## Invariants this stage must leave true

- **Article I** — every amount is `BIGINT`. There is no other numeric type in the
  schema.
- **Article II** — there is no balance column. A balance is a query. This is the one
  place where the absence of a column is the design.
- **Article III** — enforced by `BuildTransfer` and by the SQL check. Tested at both
  levels.
- **Article IV** — no `UPDATE` or `DELETE` on `entries`; reversal is a new transaction.
- **Article XI** — `created_by`, `correlation_id`, `causation_id` are non-nullable or
  explicitly nullable with a documented reason. No entry exists without an author.

## Tests you must write

- [ ] **Property test:** for random sets of legs, `BuildTransfer` accepts if and only
      if the signed sum is zero and currencies match.
- [ ] **Database test:** an unbalanced insert is rejected by the constraint. (Prove the
      database is a second line of defence, not just the Go code.)
- [ ] **Derivation test:** post N transactions, assert `EntryBalance` equals the
      expected running total, computed independently in the test.
- [ ] **Reversal test:** reverse a transaction; assert the original is `reversed`, the
      reversal is `posted`, both net to zero, and a second reversal attempt fails.
- [ ] **Immutability test:** attempt `UPDATE entries` and `DELETE FROM entries` as the
      application role; both must fail with a permission error.
- [ ] **Concurrency smoke test:** two goroutines post to the same account
      simultaneously; both succeed (posting is additive) and the balance is correct.
      Contention and holds are Stage 2 and 3.
- [ ] **Currency test:** a mixed-currency transaction is rejected with a typed error.

## Definition of done

- [ ] All three tables exist with the constraints above.
- [ ] `internal/ledger` has no import of `pgx`, `chi` or `nats`.
- [ ] The system accounts are seeded by migration, not by a script a human runs.
- [ ] The property test runs at least 10,000 cases in CI and is not skipped.
- [ ] `reference/ledger-model.md` describes the final schema, including the sign
      convention, with no drift from the migration.

## What NOT to build yet

- **Holds.** They are a separate lifecycle and belong with the saga (S3). Adding them
  now produces a half-designed hold that has to be migrated later.
- **A balance column.** It is the shortcut that undoes Article II. If performance
  becomes a problem (it will not at this stage), solve it with a *verified checkpoint*,
  in S6, with an integrity job.
- **HTTP handlers.** The ledger is a library first. A handler written now would define
  an API before the saga is understood.
- **Multi-currency transactions.** One currency per transaction. FX is two
  transactions through a settlement account, and it is not in scope.

## Failure modes

| Symptom | Cause | Tell |
|---|---|---|
| A balance that disagrees with entries | Someone added a cached column | A balance query returns a different number than the cache |
| Double reversal | Race between check and write | Two reversal rows for one original; the unique index prevents it — verify it exists |
| Suspense growing | A leg with no counterparty | The daily suspense balance is non-zero |
| Slow balance at volume | Full scan | `EntryBalance` over 10M entries takes seconds; that is S6's problem, not a reason to cache now |

## Handover

Stage 2 inherits a ledger that can post. What it cannot yet do is decide *whether* to
post: it has no notion of sufficiency, because it has no holds. Stage 2 adds the
first money-movement endpoints and meets the first concurrency requirement. Stage 3
adds holds and idempotency, which is what makes those endpoints safe to retry.
